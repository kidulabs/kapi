## Why

`kapibuild api generate` fails when installed from crates.io. The command creates a temporary Cargo project to run `schemars::schema_for!()` on user-defined types, and that temp project needs `kapi-core` as a path dependency. The path is resolved at compile time via `env!("CARGO_MANIFEST_DIR")`, which works in the kapi workspace but points into the cargo registry cache when installed from crates.io — where `kapi-core` does not exist.

```
# Works (local build)
CARGO_MANIFEST_DIR = /home/user/workspace/kapi/kapibuild
→ kapi-core path: /home/user/workspace/kapi/kapi-core  ✓

# Broken (crates.io install)
CARGO_MANIFEST_DIR = ~/.cargo/registry/src/index.crates.io-.../kapibuild-0.2.2
→ kapi-core path: ~/.cargo/registry/src/index.crates.io-.../kapi-core  ✗
```

This blocks the standard `cargo install kapibuild` workflow.

## What Changes

**Root cause**: The temporary helper project unnecessarily depends on `kapi-core`. Analysis of `generate.rs` shows the helper only calls `schemars::schema_for!()` on user-defined spec/status types — it never uses `ObjectMeta`, `ResourceKey`, or the `key()` method at runtime. The `kapi-core` dependency is only needed to make the generated wrapper code compile.

**Solution**: Strip `kapi-core` from the temporary helper project entirely:
1. Remove `use kapi_core::{ObjectMeta, ResourceKey}` from generated helper code
2. Remove `metadata: ObjectMeta` field from the wrapper struct in the helper
3. Remove the `key()` method (dead code in the helper)
4. Remove `kapi-core = { path = "..." }` from the helper's `Cargo.toml`
5. Delete `workspace_root()` function — no longer needed

This eliminates the problem at the root — no workspace discovery needed at all.

## Capabilities

### New Capabilities
(none — this is a bug fix to an existing capability)

### Modified Capabilities
- `kapibuild-api-generate`: Schema generation works regardless of how kapibuild was installed

## Impact

- **Bug fix**: `cargo install kapibuild && kapibuild api generate` will work from any directory
- **No API changes**: Output format and CLI interface remain the same
- **No new dependencies**: Helper project has fewer dependencies (removes kapi-core)
- **Deleted code**: `workspace_root()` function in `generate.rs`

## Non-goals

- Changing the schema output format
- Supporting schema generation without a compiled target project
- Adding new capabilities (e.g., schema registration — separate concern)

## Implementation Notes

The fix is surgical — only the temp helper's generated code changes:
- `write_helper_cargo_toml()`: remove `kapi-core` dependency line
- `write_helper_main_rs()`: remove `use kapi_core::{ObjectMeta, ResourceKey}`
- `generate_wrapper_code()`: remove `metadata` field and `key()` method
- `workspace_root()`: delete entirely
- `create_helper_project()`: remove `workspace_root` parameter

The user's `types/` files (generated by `generate_type_file()`) are unchanged — they legitimately depend on `kapi-core` types.
